01 / PROBLEM & PRINCIPLE
01

Agent 是一等公民

AI NATIVE WORKTREE DRAFT ONLY
CORE CLAIM

AI 全程参与需求、设计、实现、测试、审查与交付，但 AI 输出只是草案： 最终决策、代码合并与验收结论必须由人工或主代理复核（仓库以 AI_WORKFLOW.md 固化该规则）。

01

参与有记录

每次 AI 参与都按「参与范围 / 人工修正 / 验证证据 / 剩余风险」四段式归档； 子代理产物必须经主代理验收后才能进入主工作区。

02

验证优先于文字

「可执行验证优先于文字说明；没有跑过的命令不能写成已通过。」 每个改动都要留下可复现命令，CI 本地可跑，QPS 产物只收真实运行时基准。

03

分层边界约束

领域能力层不能反向依赖产品接口、运行时、供应商 SDK 或部署环境； Gin 只停留在产品接口层，应用层与领域层不依赖框架类型。

协作方式
· 默认从 main 拉任务分支，并为每条工作线创建独立 git worktree（scripts/git-worktree.sh）。
· 高风险改动（订单、库存、金额、权限、迁移、数据一致性）必须人工复核，并先写失败测试再改实现。
· 架构、运行时、供应商或框架假设必须落到 docs/architecture.md、ADR 或对应工作流文档。

事实源：backend/internal/order/domain/order_status.go
· 蓝色节点 = 主链路：CREATED → PAID → SHIPPED → FINISHED；青色节点 = 退款分支 REFUNDING

03 / HIGHLIGHT · AGENT-TO-UI

核心亮点：A2UI 流式界面生成

POST /api/ai/a2ui 接收 surface_id、user_intent 与可选 context_json，返回 A2UI v0.9 协议的多行 NDJSON 指令流： createSurface / updateComponents / updateDataModel。 前端 frontend/src/app.ts 的 a2uiRenderPanel 逐行解析 JSONL 并按指令装配组件树。

HOW IT WORKS
01 · 上下文富化

service_ai.go 的 GenerateA2UISurface 解析用户意图中的预算与场景，调用 ListProducts 查询在线商品， 把预算内商品注入 context_json。

02 · Provider 生成

backend/internal/ai.AIProvider 契约输出 A2UI v0.9 NDJSON； AI_PROVIDER=grpc 时经 gRPC 调用独立 ai-service 容器 （api/proto/ai/v1/ai.proto 定义 A2UIService）。

03 · 前端装配

逐行解析指令：Card / Column / Row / Text / Button / List / Image / Slider， 支持 formatString 函数调用、列表子作用域与 add_to_cart 动作。

安全边界

前端只渲染声明式 UI，不执行任何 Agent 代码；AI 输出只能作为建议， 不能直接改动价格、库存、权限、订单状态或退款结算结果。

04 / ENGINEERING

工程化能力：门禁可复现，指标只信真实运行时

01

CI 统一门禁

.github/workflows/ci.yml 是 PR 与 main push 的统一入口；后端、前端、AI service、安全、Docker 子 workflow 收敛为 workflow_call，本地用 ci/scripts/*.sh 复现同一套检查。

02

质量指标门禁

backend-test-metrics.sh 阻断回退：总覆盖率 65.0%、应用层 80.0%、 HTTP 层 60.0%、AI 95.0%、领域 95.0%、测试数量 55； 连库时 PostgreSQL 仓储覆盖率门槛提高到 75.0%。

03

真实运行时基准口径

README 性能表与 CI 产物（backend-postgres-http-qps.txt、 backend-rabbitmq-qps.txt）只收 PostgreSQL/Redis/RabbitMQ-backed 基准； 内存仓储、空 publisher 与模拟延迟 benchmark 不允许进入 CI artifact 或性能表。

04

幂等下单与并发安全

POST /api/orders 携带 Idempotency-Key； 已成功的状态变更重复调用返回当前订单视图。UpdateOrderStatus 用 SELECT … FOR UPDATE + AND status = fromStatus 原子迁移，防止丢失更新。

05

极端并发测试

PostgreSQL 稳定性测试覆盖脏读/幻读/写偏斜/死锁等场景： 200 并发抢 50 库存不超卖、并发支付不重复确认、并发支付与取消不产生库存损坏（ repository_stability_test.go）。

06

可观测性

Prometheus 经 /metrics 暴露 redcart_http_requests_total 与 redcart_http_request_duration_seconds（15s 采集、7d 保留）； Pyroscope Go push mode 由环境变量可选启用，默认关闭。

TRADE-OFF

异步事件边界怎么选：发件箱 vs 同步副作用

✓订单状态变更先写入数据库 outbox 表，再经 relay 轮询发布到 RabbitMQ（exchange 默认 redcart.events），发布器启用 confirm 模式、失败进死信、FOR UPDATE SKIP LOCKED 轮询。
✓业务写入与事件入箱在同一数据库事务内，保证「先记后发」的强一致；消费侧有 event_id 幂等去重与 DLX 死信队列。
✓事件成为「逻辑服务」之间的边界：未来通知、分析、库存等消费者可以独立成进程，订单核心服务仍保留在单体内部，不引入 Saga/TCC。
✓设计评审构建的控制变量 benchmark（AI_WORKFLOW.md 会话记录）：模拟 3 个 500μs 下游调用时，发件箱模式吞吐提升约 365 倍；该数据仅用于决策，不进入 README 性能表。
✗每次订单状态变更后，订单服务直接同步调用下游（通知、分析等），请求路径被下游延迟拖慢。
✗下游失败会污染交易路径：核心订单事务与外部副作用耦合，难以回滚与重试。
✗扩展性差：新增消费者需要改动订单服务代码，而不是独立订阅事件。
✓对照基准 BenchmarkCreateOrderSyncSideEffects 用于量化差距，证明发件箱收益是吞吐提升而不是实现偏好。
